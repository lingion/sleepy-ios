# Add courses parity with Android v1.0.63

The management Add Courses action freezes an explicit existing target table ID. Its source chooser includes existing schedules, educational-system import and drafts, WakeUp shares, pasted text, files, and manual entry. Manual entry opens the existing course editor with that target. Batch sources enter a shared group selector, defaulting to all groups, before the conflict preview. Empty or period-only data cannot enter this flow.

Group identity uses a nonblank authoritative group ID, falling back to trimmed course name and teacher. Selection preserves every meeting in each chosen group and all parser metadata. Copying an existing schedule reads its effective bound period table and preserves authoritative group IDs. Every preview and write uses the captured target, including name and effective time metadata. New parser deliveries invalidate previous preview actions.

Educational-system results and restored parsed drafts use the same selector and decision components inside the educational-system child flow, so its cancellation reducer remains authoritative. Restored drafts retain the continue/keep/delete choice until a successful import. Fresh Add Courses imports create no draft automatically; cancelling exits without leaving a draft. The conflict preview defaults to backing up the original schedule and skipping conflicting incoming meetings. Its switches map to one repository transaction that rereads current courses, freezes an independent backup, and appends only accepted meetings. Existing target time slots take precedence; own-time meetings and week parity participate in conflict checks. One undo reverses both backup and append. Existing preview UUID guards remain in place. The management Create Schedule entry proceeds directly to new-table configuration; it cannot replace the selected schedule.

Validation uses real in-memory repositories for source hydration, group filtering and target ownership, plus management source/manual entry UI coverage. Root runs builds and simulator verification centrally. This scope and implementation are explicitly authorized by the parent task; no commit is made in the shared checkout.
